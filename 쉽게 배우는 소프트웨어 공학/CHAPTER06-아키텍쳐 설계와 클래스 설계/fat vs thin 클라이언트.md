
## 1. 개념 한 줄 정의

| 구분          | 정의                                       |
| ----------- | ---------------------------------------- |
| Thin Client | 클라이언트는 입력·출력만 담당하고 대부분의 로직과 처리는 서버가 담당한다 |
| Fat Client  | 클라이언트가 비즈니스 로직과 처리를 상당 부분 담당한다           |

---

## 2. 핵심 특징 비교

| 구분       | Thin Client           | Fat Client             |
| -------- | --------------------- | ---------------------- |
| 로직 위치    | 서버 중심이다               | 클라이언트 중심이다             |
| 클라이언트 역할 | 화면 렌더링, 입력 전달이다       | 로직 처리, 상태 관리, 화면 렌더링이다 |
| 서버 역할    | 비즈니스 로직, 연산, 데이터 처리이다 | API 제공, 데이터 저장이다       |
| 배포       | 서버 배포 한 번이면 된다        | 클라이언트 업데이트가 필요하다       |
| 성능 의존성   | 네트워크 의존도가 높다          | 로컬 성능 의존도가 높다          |
| 오프라인     | 거의 불가능하다              | 가능하거나 유리하다             |
| 보안       | 서버에서 통제하기 쉽다          | 클라이언트 변조 위험이 있다        |
| 유지보수     | 중앙 집중 관리가 쉽다          | 버전 관리가 어렵다             |

---

## 3. 실제 서비스 예시

### 3-1. Thin Client 실제 예시

| 서비스           | 이유                       |
| ------------- | ------------------------ |
| 은행 인터넷뱅킹 웹    | 금융 로직을 클라이언트에 두면 위험하다    |
| 공공기관 행정 웹     | 배포 통제와 보안이 최우선이다         |
| 사내 ERP 웹      | 사용자 환경이 다양하고 중앙 통제가 필요하다 |
| 초기 웹 서비스(MPA) | 개발 단순성과 유지보수가 목적이다       |

**구조 예시**

* JSP / Thymeleaf
* 서버에서 HTML 생성
* 컨트롤러 + 서비스 + DB가 핵심이다
* 브라우저는 화면만 보여준다

---

### 3-2. Fat Client 실제 예시

| 서비스                | 이유                     |
| ------------------ | ---------------------- |
| 모바일 앱(카카오톡, 인스타그램) | 즉각적인 반응성과 오프라인 처리 때문이다 |
| SPA 웹(React, Vue)  | UX와 인터랙션이 중요하다         |
| 게임 클라이언트           | 실시간 처리와 로컬 연산이 필수다     |
| 데스크톱 앱             | 장치 자원 활용이 필요하다         |

**구조 예시**

* React / Flutter / Android / iOS
* 상태 관리, 로직이 클라이언트에 있다
* 서버는 REST API 또는 GraphQL 제공만 한다

## 4. 왜 그렇게 생겼는가 (핵심 이유)

### Thin Client가 선택되는 이유

1. **보안**

   * 금융, 공공 서비스는 로직 노출이 치명적이다
   * 서버에 로직을 두는 것이 안전하다

2. **운영 효율**

   * 서버 한 번 배포하면 전체 반영이다
   * 사용자 PC 환경을 고려하지 않아도 된다

3. **단순성**

   * 구조가 단순하다
   * 장애 포인트가 명확하다

→ **통제, 안정성, 관리가 중요할수록 Thin Client이다**

---

### Fat Client가 선택되는 이유

1. **사용자 경험**

   * 즉각적인 반응이 가능하다
   * 화면 전환이 빠르다

2. **확장성**

   * 서버는 API만 담당한다
   * 트래픽 분산에 유리하다

3. **복잡한 UI**

   * 실시간 인터랙션, 상태 변화 처리에 유리하다

→ **UX, 성능, 인터랙션이 중요할수록 Fat Client이다**

---

## 5. 오해하면 안 되는 포인트

| 오해                   | 실제                |
| -------------------- | ----------------- |
| SPA = 무조건 Fat Client | 로직이 어디 있느냐가 기준이다  |
| Thin Client는 구식이다    | 금융·공공에서는 여전히 정답이다 |
| Fat Client는 서버가 단순하다 | 서버 설계 난이도는 오히려 높다 |

---

## 6. 한 줄 요약

* **Thin Client**는 통제와 보안을 위해 서버에 모든 것을 둔다
* **Fat Client**는 UX와 성능을 위해 클라이언트에 힘을 준다
* 어느 쪽이 우수한 것이 아니라 **문제 성격에 따른 선택**이다
