

# 1. 접근통제 모델 큰 그림

접근통제 모델은
**누가(주체) 무엇을(객체) 어떤 기준으로 접근할 수 있는가**를 정의한다.

핵심 차이는
1. **권한을 누가 결정하는가**
2. **악성코드에 얼마나 강한가** 이다.

---

# 2. DAC (Discretionary Access Control)

## 개념

DAC는 **객체의 소유자가 접근 권한을 결정하는 방식**이다.
운영체제는 사용자의 판단을 그대로 따른다.

---

## 특징

| 항목       | 내용       |
| -------- | -------- |
| 권한 결정 주체 | 사용자(소유자) |
| 권한 변경    | 자유롭다     |
| 정책 강제성   | 없다       |
| 유연성      | 높다       |
| 보안성      | 낮다       |

---

## 트로이목마·멀웨어 취약 이유

* 프로그램이 **사용자 권한을 그대로 상속**한다
* 사용자를 속이면 **모든 권한을 획득**한다
* 정보 흐름 통제가 불가능하다

### 예시

* 사용자가 악성 PDF 실행
* 해당 프로그램이 사용자 문서 전부 접근
* OS는 정상 행위로 간주

👉 **DAC는 트로이목마에 구조적으로 취약하다**

---

## 실무 예시

* Linux/Unix 파일 권한 (rwx)
* 개인 PC 환경
* 개발 서버 기본 권한 모델

---

# 3. MAC (Mandatory Access Control)

## 개념

MAC는 **시스템이 강제하는 보안 정책에 따라 접근을 제어하는 방식**이다.
사용자는 정책을 임의로 변경할 수 없다.

---

## 특징

| 항목       | 내용    |
| -------- | ----- |
| 권한 결정 주체 | 시스템   |
| 권한 변경    | 불가능   |
| 정책 강제성   | 매우 강함 |
| 유연성      | 낮다    |
| 보안성      | 매우 높다 |

---

## 트로이목마·멀웨어 대응

* 프로그램이 사용자 권한을 가져도
* **정책 위반 접근은 차단**한다
* 정보 흐름을 통제한다

### 예시

* 기밀 등급 파일을 일반 프로세스가 읽지 못한다
* 악성코드가 실행되어도 유출 불가

👉 **트로이목마 방어에 가장 강한 모델**

---

## 실무 예시

* 군사·정부 보안 시스템
* SELinux
* AppArmor

---

# 4. RBAC (Role-Based Access Control)

## 개념

RBAC는 **사용자가 아닌 역할(Role)에 권한을 부여**하는 방식이다.
사용자는 역할을 부여받아 권한을 획득한다.

---

## 특징

| 항목       | 내용       |
| -------- | -------- |
| 권한 결정 단위 | 역할       |
| 관리 난이도   | 낮다       |
| 확장성      | 매우 좋다    |
| 정책 강제성   | 중간       |
| 보안성      | DAC보다 높다 |

---

## 트로이목마·멀웨어 관점

* 악성코드는 **해당 역할 권한까지만 가능**
* 최소 권한 원칙 적용 가능
* DAC보다는 안전
* MAC보다는 약함

👉 **조직 보안과 운영 효율의 균형 모델**

---

## 실무 예시

* 기업 시스템 권한 관리
* 클라우드 IAM (AWS IAM, GCP IAM)
* DB 권한 관리
* 사내 포털 (관리자 / 직원 / 외부인)

---

# 5. 보안 관점 핵심 비교 (중요)

## 트로이목마·멀웨어 대응력

| 모델   | 대응력   | 이유            |
| ---- | ----- | ------------- |
| DAC  | 매우 약함 | 사용자 권한 그대로 상속 |
| RBAC | 중간    | 역할 범위로 제한     |
| MAC  | 매우 강함 | 시스템 정책이 강제    |

---

## 전체 비교 표

| 구분       | DAC   | RBAC    | MAC     |
| -------- | ----- | ------- | ------- |
| 권한 결정    | 사용자   | 역할      | 시스템     |
| 사용자 재량   | 높음    | 제한적     | 없음      |
| 정책 강제    | 없음    | 중간      | 강함      |
| 관리 편의성   | 높음    | 매우 높음   | 낮음      |
| 트로이목마 방어 | 매우 약함 | 중간      | 매우 강함   |
| 실무 사용    | 개인·개발 | 기업·클라우드 | 군·보안시스템 |

---

# 6. 실무에서 실제로는 어떻게 쓰나

현실에서는 **하나만 쓰지 않는다**.

* 기본 구조: **DAC**
* 조직 관리: **RBAC**
* 핵심 보안 영역: **MAC**

예시:

* Linux 서버

  * 기본 파일 권한: DAC
  * 사용자 그룹 관리: RBAC
  * 중요 프로세스 보호: SELinux(MAC)

---

# 7. 한 줄 요약

* DAC는 편하지만 트로이목마에 가장 취약하다
* MAC는 가장 안전하지만 불편하다
* RBAC는 실무에서 가장 많이 쓰이는 균형 모델이다

좋다. 지금까지 나온 개념을 **한 덩어리로** 정리한다.
이건 시험·면접·실무 설명용으로 그대로 써도 된다.

# 접근통제 모델과 트로이목마·멀웨어 보안 정리

## 1. 큰 그림

보안에서 접근통제 모델의 차이는
**“보안 판단을 누가 하는가”**의 차이다.

* 사람에게 맡기면 약해진다
* 시스템이 강제할수록 강해진다

트로이목마와 멀웨어는
**시스템이 아니라 사람을 공격한다**.

---

## 2. “사람을 속인다”의 정확한 의미

보안에서 사람을 속인다는 것은
**사용자가 보안 판단을 대신하게 만드는 것**이다.

* 정상 프로그램처럼 위장한다
* 사용자가 실행하도록 유도한다
* 실행되는 순간, 권한은 합법적으로 위임된다

이때 시스템은 공격을 감지하지 못한다.

---

## 3. DAC (Discretionary Access Control)

### 개념

DAC는 **객체의 소유자인 사용자가 접근 권한을 결정하는 모델**이다.

---

### 특징

| 항목      | 내용     |
| ------- | ------ |
| 권한 결정   | 사용자    |
| 프로그램 신뢰 | 사용자 판단 |
| 정책 강제   | 없음     |
| 보안 강도   | 낮다     |

---

### 트로이목마·멀웨어 관점

* 프로그램은 사용자 권한을 그대로 상속한다
* 사용자를 속이면 모든 권한을 얻는다
* OS는 이를 정상 행위로 본다

👉 **사람을 속이면 보안이 무력화된다**

---

### 실무 예시

* Linux 기본 파일 권한
* 개인 PC 환경
* 개발 서버

---

## 4. RBAC (Role-Based Access Control)

### 개념

RBAC는 **사용자가 아닌 역할(Role)에 권한을 부여하는 모델**이다.

---

### 특징

| 항목    | 내용    |
| ----- | ----- |
| 권한 기준 | 역할    |
| 관리 효율 | 매우 높다 |
| 최소 권한 | 적용 가능 |
| 보안 강도 | 중간    |

---

### 트로이목마·멀웨어 관점

* 악성코드는 해당 역할 범위까지만 가능하다
* 피해 확산이 제한된다
* 사용자의 판단이 완전히 제거되지는 않는다

👉 **사람 실수를 줄이지만 없애지는 못한다**

---

### 실무 예시

* 기업 권한 관리
* 클라우드 IAM
* DB 권한 모델

---

## 5. MAC (Mandatory Access Control)

### 개념

MAC는 **시스템이 강제하는 보안 정책에 따라 접근을 통제하는 모델**이다.

---

### 특징

| 항목     | 내용    |
| ------ | ----- |
| 권한 결정  | 시스템   |
| 사용자 재량 | 없음    |
| 정책 강제  | 매우 강함 |
| 보안 강도  | 매우 높다 |

---

### 트로이목마·멀웨어 관점

* 프로그램이 실행되어도 정책 위반은 차단된다
* 사용자 판단이 무효화된다
* 정보 흐름 자체가 통제된다

👉 **속아도 깨지지 않는다**

---

### 실무 예시

* 군사·정부 시스템
* SELinux
* AppArmor

---

## 6. 왜 보안 차이가 발생하는가

### 핵심 질문 하나로 정리된다

> “프로그램이 내 대신 행동해도 되는가?”

| 모델   | 대답            |
| ---- | ------------- |
| DAC  | 무조건 된다        |
| RBAC | 역할 한도 내에서 된다  |
| MAC  | 정책이 허용할 때만 된다 |

---

## 7. 전체 비교 표

| 구분       | DAC   | RBAC    | MAC    |
| -------- | ----- | ------- | ------ |
| 보안 판단 주체 | 사용자   | 역할      | 시스템    |
| 사람 의존도   | 매우 높음 | 중간      | 거의 없음  |
| 트로이목마 방어 | 매우 약함 | 중간      | 매우 강함  |
| 운영 편의성   | 높음    | 높음      | 낮음     |
| 실무 사용    | 개인·개발 | 기업·클라우드 | 고보안 영역 |

---

## 8. 최종 요약 한 문단

접근통제 모델의 보안 차이는
**사람의 판단을 얼마나 배제했는가**에서 발생한다.
트로이목마와 멀웨어는 시스템을 뚫지 않고,
사람이 “괜찮다”라고 판단하게 만든다.
DAC는 그 판단을 그대로 신뢰하고,
RBAC는 일부 제한하며,
MAC는 아예 무시한다.
