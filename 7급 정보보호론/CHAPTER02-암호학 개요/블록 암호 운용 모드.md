# 블록 암호 운용 모드 상세 분석

## 1. ECB (Electronic CodeBook) 모드

### 개념
가장 기본적인 블록 암호 운용 모드로, 각 평문 블록을 독립적으로 암호화한다. 동일한 평문 블록은 항상 동일한 암호문 블록을 생성한다.

### 특징
1. **독립적 암호화**: 각 블록이 독립적으로 암호화되므로 병렬 처리가 가능
2. **오류 전파 없음**: 한 블록의 오류가 다른 블록에 영향을 미치지 않음
3. **패딩 필요**: 마지막 블록이 블록 크기에 맞지 않으면 패딩 추가 필요
4. **보안 취약**: 동일한 평문 블록 → 동일한 암호문 블록이므로 패턴 노출
5. **초기화 벡터 불필요**: 별도의 IV가 필요 없음

### 실무 응용
- **안전하지 않은 경우**: 이미지, 비디오 암호화 (시각적 패턴 노출)
- **제한적 사용**: 암호화된 데이터베이스 키 저장 (짧은 고정 길이 데이터)
- **특수 목적**: 단일 블록 암호화 필요 시 (예: 토큰 생성)
- **절대 금지**: 대량 데이터, 텍스트 문서, 패턴이 있는 데이터

## 2. CBC (Cipher Block Chaining) 모드

### 개념
이전 암호문 블록을 현재 평문 블록과 XOR한 후 암호화하는 방식으로, 블록 간 연쇄적 의존성을 만든다.

### 특징
1. **연쇄적 의존성**: 각 블록 암호화에 이전 암호문 블록 사용
2. **오류 전파**: 한 블록의 오류가 다음 블록에 영향을 미침 (전파성)
3. **초기화 벡터 필요**: 첫 블록의 XOR을 위한 랜덤 IV 필요
4. **패딩 필요**: 블록 크기 정렬을 위한 패딩 필요
5. **암호화 순차적, 복호화 병렬 가능**: 복호화 시 병렬 처리 가능

### 실무 응용
- **파일 암호화**: 문서, 압축 파일, 백업 데이터
- **디스크 암호화**: 전체 디스크 볼륨 암호화
- **TLS 1.2 이전**: SSL/TLS에서 널리 사용
- **데이터베이스 필드 암호화**: 개별 레코드 암호화
- **제한적 사용**: 대역폭이 넉넉하고 지연 허용 가능한 응용

---

## 3. CFB (Cipher FeedBack) 모드

### 개념
블록 암호를 스트림 암호처럼 사용하는 모드로, 이전 암호문을 암호화하여 키 스트림을 생성하고 평문과 XOR한다.

### 특징
1. **자가 동기화**: 암호문 피드백으로 부분적 자가 동기화 가능
2. **스트림 암호 모드**: 블록 암호를 스트림 암호처럼 동작
3. **오류 전파 제한적**: r비트 CFB에서 오류는 최대 블록 크기까지 전파
4. **패딩 불필요**: 스트림 방식이므로 패딩 필요 없음
5. **초기화 벡터 필요**: 시작점을 위한 IV 필요

### 실무 응용
- **통신 프로토콜**: 비동기적 통신 환경 (오류 자동 복구 필요)
- **실시간 데이터**: 오디오/비디오 스트리밍 (부분적 패킷 손실 허용)
- **레거시 시스템**: 오래된 통신 장비와의 호환성
- **제한적 사용**: 오류 복구 기능이 중요한 특수 통신

---

## 4. OFB (Output FeedBack) 모드

### 개념
암호화 출력을 피드백하여 키 스트림을 생성하는 모드로, 암호화와 복호화가 동일한 키 스트림을 사용한다.

### 특징
1. **동기식 스트림 암호**: 키 스트림이 평문/암호문과 독립적
2. **오류 전파 없음**: 비트 오류가 확산되지 않고 해당 위치에만 영향
3. **사전 계산 가능**: IV와 키만 알면 키 스트림 미리 계산 가능
4. **패딩 불필요**: 스트림 암호 방식
5. **초기화 벡터 중요**: IV 재사용 시 심각한 보안 문제 발생

### 실무 응용
- **위성 통신**: 오류 전파가 치명적인 환경
- **저대역폭 통신**: 사전 계산으로 실시간 처리 부하 감소
- **음성 통신**: 비트 오류가 음질에만 영향을 미치도록
- **제한적 권장**: IV 관리가 철저히 가능한 환경에서만

---

## 5. CTR (CounTeR) 모드

### 개념
카운터 값을 암호화하여 키 스트림을 생성하는 모드로, 블록 암호를 병렬화 가능한 스트림 암호로 변환한다.

### 특징
1. **완전 병렬화**: 모든 블록의 암호화/복호화 병렬 처리 가능
2. **임의 접근 가능**: 특정 블록만 암호화/복호화 가능
3. **오류 전파 없음**: 각 블록 독립적 처리
4. **패딩 불필요**: 스트림 암호 방식
5. **카운터 관리 중요**: 카운터 중복 절대 방지 필요

### 실무 응용
- **고성능 암호화**: SSD, RAID 시스템의 디스크 암호화
- **데이터베이스 암호화**: 특정 레코드만 접근/수정 가능
- **TLS 1.2 이상**: 현대 인터넷 통신 표준
- **클라우드 저장소**: 대용량 파일의 병렬 암호화
- **멀티미디어 스트리밍**: 임의 지점 접근 가능한 미디어

## 7. 추가 상세 비교

### 7.1 IV/Nonce 요구사항 비교

| 모드 | IV 특성 | 길이 | 재사용 위험 | 관리 중요도 |
|------|---------|------|-------------|------------|
| **ECB** | 불필요 | - | - | 낮음 |
| **CBC** | 랜덤, 예측불가 | 블록 크기 | 중간 | 높음 |
| **CFB** | 랜덤, 예측불가 | 블록 크기 | 높음 | 매우 높음 |
| **OFB** | 유일 (랜덤 권장) | 블록 크기 | 매우 높음 | 매우 높음 |
| **CTR** | 유일 (Nonce+Counter) | 블록 크기 | 매우 높음 | 매우 높음 |

### 7.2 오류 전파 상세 분석

```
ECB: [블록1][블록2][블록3]  ← 오류가 국한됨
      오류시↗          → 오류 블록만 영향

CBC: [블록1]→[블록2]→[블록3]  ← 오류가 연쇄 전파
      오류시↗    → 블록2 복호화 오류
                  → 블록3 정상 복호화

CFB: [암호문1]→[암호문2]→[암호문3]  ← 제한적 오류 전파
       오류시↗      → 암호문2 복호화 오류
                    → 암호문3 정상 복호화 (블록 크기 후)

OFB: [키스트림]→[키스트림]→[키스트림]  ← 오류 전파 없음
      평문⊕키스트림 → 암호문
       오류시↗          → 해당 비트만 영향

CTR: [카운터1][카운터2][카운터3]  ← 오류 전파 없음
      각각 키스트림 생성
       오류시↗          → 해당 블록만 영향
```

## 8. 실무 적용 가이드라인

### 8.1 현대적 권장사항

**우선 순위 1: CTR 모드 또는 GCM 모드**
```
사용처: TLS 1.3, VPN, 디스크 암호화, 클라우드 저장소
이유: 병렬성, 성능, 임의 접근 가능
주의점: 카운터/Nonce 중복 절대 방지
```

**우선 순위 2: CBC 모드 (레거시/제한적)**
```
사용처: 기존 시스템 호환성, 특정 규격 요구
이유: 광범위한 지원, 검증된 안전성
주의점: 패딩 오라클 공격 방지, 랜덤 IV 사용
```

**사용 금지: ECB 모드**
```
금지 이유: 패턴 노출, 보안성 낮음
예외: 단일 블록 암호화(키 암호화 등)
```

### 8.2 산업별 적용 현황

**금융 업계 (ISO 8583 등)**:
- 과거: CBC 모드 주류
- 현재: CTR + MAC 또는 GCM/CCM으로 전환 중
- EMV 칩: 다양한 모드 사용 (업체별 차이)

**통신 프로토콜**:
- TLS 1.0-1.2: CBC 모드 (현재는 권장되지 않음)
- TLS 1.3: AEAD 모드만 허용 (GCM, CCM, ChaCha20-Poly1305)
- IPSec: CBC, CTR, GCM 지원

**저장소 암호화**:
- 파일 시스템: XTS 모드 (CBC 변형)
- 데이터베이스: CTR 모드 (임의 접근 위해)
- 클라우드: 서버측 암호화에 CTR/GCM 사용

## 9. 보안 고려사항 및 모범 사례

### 9.1 공통 보안 원칙

1. **키 관리**
   - 안전한 키 생성 (진난수 사용)
   - 정기적 키 회전
   - 키 저장소 보안 (HSM 등)

2. **IV/Nonce 관리**
   - 예측 불가능한 값 사용
   - 절대 재사용하지 않음
   - 충분한 엔트로피 보장

3. **패딩 공격 방지**
   - CBC 모드 시 패딩 오라클 공격 주의
   - 상수 시간 패딩 검증 구현
   - 또는 패딩 없는 모드(CTR, GCM) 사용

### 9.2 모드별 특별 주의사항

**CBC 모드**:
- 초기화 벡터(IV)를 랜덤하게 생성
- 메시지 인증 코드(MAC) 추가 사용
- 패딩 오라클 공격 방지

**CTR 모드**:
- 카운터 중복 절대 방지
- Nonce와 카운터 조합 설계
- 64비트 Nonce + 64비트 카운터 권장

**CFB/OFB 모드**:
- IV 재사용 시 심각한 보안 문제
- 키 스트림 재사용으로 평문 노출 위험
- 현대 시스템에서는 권장되지 않음

### 9.3 인증 암호화(AEAD)로의 전환

**현대적 접근**:
```
과거: 암호화 모드 + 별도 MAC
문제: 구성 오류, 취약한 결합 방식

현재: 통합 인증 암호화 모드
- GCM (Galois/Counter Mode): AES-CTR + GMAC
- CCM (Counter with CBC-MAC)
- ChaCha20-Poly1305
```

**AEAD 모드 장점**:
1. 단일 작업으로 기밀성 + 무결성 보장
2. 구현 오류 최소화
3. 표준화된 안전한 구성
4. 성능 효율적

## 10. 실제 구현 예시

### 10.1 OpenSSL 명령줄 예시

```bash
# CBC 모드 (AES-256)
openssl enc -aes-256-cbc -in plain.txt -out encrypted.bin -K [키] -iv [IV]

# CTR 모드 (AES-256)  
openssl enc -aes-256-ctr -in plain.txt -out encrypted.bin -K [키] -iv [IV]

# GCM 모드 (인증 암호화)
openssl enc -aes-256-gcm -in plain.txt -out encrypted.bin -K [키] -iv [IV] -aad [추가인증데이터]
```

### 10.2 프로그래밍 인터페이스 (의사 코드)

```python
# CTR 모드 구현 예시 (간소화)
def aes_ctr_encrypt(plaintext, key, nonce):
    ciphertext = bytearray()
    
    for i in range(0, len(plaintext), 16):
        # 카운터 블록 생성: Nonce + Counter
        counter_block = nonce + int_to_bytes(i // 16)
        
        # 카운터 암호화 → 키 스트림 생성
        keystream = aes_encrypt(counter_block, key)
        
        # 평문과 키 스트림 XOR
        block = plaintext[i:i+16]
        encrypted_block = xor_blocks(block, keystream)
        ciphertext.extend(encrypted_block)
    
    return ciphertext
```

## 11. 결론 및 권장사항 요약

### 11.1 현실적 조언

**신규 시스템 설계 시**:
```
1순위: GCM 모드 (인증 암호화 통합)
- 이유: 기밀성 + 무결성, 성능 좋음, 표준화됨

2순위: CTR 모드 + HMAC (별도 인증)
- 이유: 높은 병렬성, 임의 접근 가능

3순위: ChaCha20-Poly1305
- 이유: 소프트웨어 최적화, 모바일 친화적
```

**기존 시스템 유지보수 시**:
- CBC 모드: 패딩 오라클 방지 조치 적용
- 레거시 모드: 점진적 현대 모드로 전환 계획 수립
- 보안 감사: 현재 사용 모드의 취약점 정기 평가

1. **데이터 특성 고려**
   - [ ] 구조화된 데이터? → 패턴 노출 방지 모드
   - [ ] 스트리밍 데이터? → 오류 전파 고려
   - [ ] 대용량 데이터? → 병렬성 고려

   - [ ] 기밀성만 필요? → 기본 암호화 모드
   - [ ] 무결성도 필요? → AEAD 모드
   - [ ] 재전송 공격 방지? → Nonce/카운터 관리

3. **성능 제약사항**
   - [ ] 하드웨어 가속 가능? → AES 기반 모드
   - [ ] 저전력 장치? → 경량 알고리즘 고려
   - [ ] 실시간 처리 필요? → 지연 시간 고려

   - [ ] 기존 시스템과 통신? → 공통 모드 확인
   - [ ] 표준 규격 준수? → 산업 표준 확인
   - [ ] 미래 확장성? → 유연한 설계

블록 암호 운용 모드 선택은 단순히 암호화 방식을 넘어 시스템 전체의 보안, 성능, 유지보수성을 결정하는 중요한 설계 결정이다.

## CBC 암호화의 본질

* 암호화는 **체인을 “만드는 과정”**이다
* 현재 블록을 암호화하려면 **이전 암호문이 반드시 필요**하다

수식 관점에서 보면

* Cᵢ = Eₖ(Pᵢ ⊕ Cᵢ₋₁)

여기서 Cᵢ₋₁이 아직 없으면
Pᵢ ⊕ Cᵢ₋₁ 자체를 만들 수 없다.

그래서 암호화는 **완전한 체인 구조**이고
병렬 처리가 안 된다.

---

## CBC 복호화의 본질

* 복호화는 **이미 완성된 체인을 “푸는 과정”**이다
* 암호문 블록들은 **이미 전부 존재**한다

수식은 이렇다.

* Pᵢ = Dₖ(Cᵢ) ⊕ Cᵢ₋₁

중요한 점은

* Dₖ(Cᵢ)는 **Cᵢ 하나만으로 가능**하다
* Cᵢ₋₁은 단순 XOR 재료일 뿐이다

그래서

* 복호화 연산 자체는 병렬 가능
* 마지막 XOR만 이전 블록을 사용한다

---

## 한 줄로 정리

* 암호화는 **체인을 생성해야 해서 직렬**
* 복호화는 **이미 존재하는 체인을 참조만 해서 병렬 가능**

---

## 비유로 최종 정리

* 암호화: 앞사람 손을 잡아야 다음 사람이 손을 잡을 수 있다
* 복호화: 이미 다 손잡고 있으니, 각자 손만 풀면 된다

---

## 정확한 결론

> CBC에서
> **암호화는 체인 구조**이고
> **복호화는 기존 암호문에 XOR만 더해 평문을 복원하는 구조**이다.
